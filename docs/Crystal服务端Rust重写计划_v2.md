# Crystal 服务端 Rust 重写计划 2.0

> 目标：在保证与原 Crystal C# 服务端逻辑与手感高度一致的前提下，完成 Rust 全重写，并分阶段逐步优化性能、架构与可维护性，同时为未来客户端演进（高清化 / ECS 改造）打好基础。

---

## 一、背景与总体目标

- **现状**
  - 原服务端为 C# + WinForms 架构，长期运行下存在 CPU/内存占用偏高、GC 抖动、单线程瓶颈等问题。
  - 客户端仍以 Crystal / Mir2 C# 客户端为主，不做重写，但允许进行适度画质与体验优化。

- **Rust 重写的总体目标**
  - 使用 Rust + Tokio 在 64 位 Windows Server 2008 R2（`x86_64-pc-windows-msvc`）上搭建高性能、可长期演进的服务器。
  - **先 1:1 复刻行为，再逐步优化实现**：不破坏旧的玩法、节奏和手感。
  - 在相同硬件上，相比原 C# 服务端：
    - 降低 CPU/内存占用。
    - 提升可支撑并发与长时间稳定运行能力。

- **Workspace / Crate 规划（服务端）**
  - `crystal-shared-proto`：协议定义与编码解码，保证与 C# 客户端字节级兼容。
  - `crystal-server-net`：网络层（连接管理、收发包、粘包/拆包、心跳等）。
  - `crystal-server-core`：核心游戏逻辑（地图、怪物、AI、战斗、掉落、Buff 等）。
  - `crystal-server-db`：持久化（账号、角色、物品、日志等）。
  - `crystal-server-config`：配置加载、校验与（可选）热更新。
  - `crystal-server-admin`：GM/运营管理接口和工具。
  - `crystal-server-bin`：最终可执行程序，负责进程启动、配置加载、组件装配与运行。

## 二、总原则（贯穿全程）

### 2.1 先复刻行为，再优化性能

Crystal 是一个**强烈依赖时序与微实现细节**的服务器：

- 怪物寻路路径、转向时机。
- 攻击节奏、技能前后摇、硬直窗口。
- Buff 定时与多 Buff 叠加顺序。
- 怪物 AI 决策顺序、仇恨排序。
- 玩家状态更新顺序、移动插值节奏。

**如果一上来就“聪明地优化”这些行为，很容易导致：**

- Boss 手感变化、卡点失效。
- 连招时机被破坏、触发几率变化。
- 玩家积累多年的经验被“重置”，体验割裂。

> 因此：必须先追求“黑盒一致”，在此基础上再逐步优化内部实现。

### 2.2 黑盒一致性约束

在所有优化阶段中，需要尽量保持以下一致性（以旧 C# 服务端为基准）：

- **Packet 协议**：不改动现有协议格式和语义。
- **NPC 脚本输出**：对话文本、任务分支、脚本执行结果一致。
- **Tick 执行顺序**：逻辑 Tick 中系统执行的顺序保持不变（或在可控范围内等价）。
- **时序行为**：
  - 移动/攻击/施法节奏在可接受误差内一致。
  - Buff/DOT/CD 的生效与结束时间点基本一致。

## 三、阶段总览（0 → 5）

- **阶段 0：基础框架稳定化（复刻行为，不做优化）**
- **阶段 1：验证阶段（行为一致性 Record/Replay 测试）**
- **阶段 2：轻量优化（数据结构 / Timer / AOI 内部实现）**
- **阶段 3：中型优化（Frame Loop / 日志 / Packet 池化）**
- **阶段 4：大中型优化（AI 调度 / 多线程调度器）**
- **阶段 5：高级优化（AOI / 寻路 / 战斗逻辑重做，允许行为变化）**

后续阶段尽量做到“前一阶段完全稳定后再进入下一阶段”，避免多处同时大改难以定位问题。

## 四、阶段 0：基础框架稳定化（必须保持原行为）

**目标**：在 Rust 中完整重写现有 C# 服务端代码，使整体行为尽可能 1:1 复刻，仅语言与实现方式变化。

### 4.1 模块划分（保持逻辑但整理结构）

建议将当前逻辑按功能模块化，避免逻辑散乱：

- `game-core`：
  - 核心世界/地图/怪物/玩家等逻辑。
  - 怪物 Run/Tick、AI、战斗、Buff、掉落等。
  - **此阶段尽量保持与 C# 原版 1:1 映射。**

- `game-data`：
  - 技能、怪物、地图、掉落、NPC 脚本等配置数据的加载与管理。

- `game-sim`（或 world/tick）：
  - Tick 驱动器 / 世界模拟器。
  - 保持原有 Tick 调度顺序和粒度。

- `net-core`：
  - 协议层、会话管理、收发包与分发。

- `aoi-core`：
  - AOI（九宫格等）逻辑，保持原查找与广播方式不变。

> 重点：**不要改变 Tick 执行顺序与关键系统的调用链，只在模块边界做整理。**

### 4.2 阶段 0 验收

- 同一场景下（典型地图 / 副本）：
  - 怪物走位、攻击节奏、仇恨变更与 C# 版肉眼观察基本一致。
  - NPC 对话、任务流程、奖励结果一致。
- 暂不追求性能提升，只要不明显劣于 C# 即可。


---

## 五、阶段 1：验证阶段（行为一致性 Record/Replay）

**目标**：为后续任何优化提供“真基线”，证明 Rust 服与 C# 服在黑盒行为上高度一致。

### 5.1 Record：在旧 C# 服务端录制行为

在旧服上实现或外挂一套录制系统，收集：

- 玩家输入事件：
  - 移动（方向、目标格子）。
  - 攻击（目标、技能 ID）。
  - 施法、物品使用、物品移动等。

- NPC 和怪物相关：
  - 刷怪点与刷怪事件（位置、时间）。
  - NPC 脚本触发事件（对话选项、任务交互等）。

- 定时器与 Tick 信息：
  - Buff/CD/AI Tick 时间戳。
  - 可选：服务端 frame/tick 号。

- 收发包顺序（可选）：
  - 关键场景下抓包，用于更精细的对齐和问题排查。

### 5.2 Replay：在 Rust 服上回放并对比

- 在 Rust 服加入 Replay 模式：
  - 按相同时间轴/帧顺序驱动世界（使用已录制的输入）。

- 对比输出：
  - 玩家/怪物位置轨迹。
  - NPC 对话结果与任务状态。
  - 战斗结果（受伤/死亡帧、剩余血量）。
  - Buff 生效/结束时间点（Tick 级误差容忍）。

### 5.3 阶段 1 验收

- 多组典型“战斗/副本/野外刷怪”剧本在 Replay 下，Rust 服与 C# 服的结果至少 **95%+ 行为吻合**。
- 形成一份差异清单，对误差归因（浮点 vs 整数、时间粒度、随机种子、边界判断等）。

## 六、阶段 2：轻量优化（不改变行为，收益明显）

这些优化只改内部实现和数据结构，不动算法与宏观时序，目标是 CPU -30%~50%。

### 6.1 更合理的数据结构（零行为风险）

- 将原基于 C# 集合的逻辑，在 Rust 中替换为更合适的数据结构：
  - `Vec` / `VecDeque` 替代链表、队列类结构。
  - `FxHashMap` / `hashbrown::HashMap` 提升 Hash 查找性能。
  - `SmallVec` 用于 AOI 邻居列表、小集合（避免堆分配）。
  - `slab`/`IndexVec` 管理玩家、怪物等“句柄式对象池”。
  - `DashMap` 用于读多写少、需要并发读的管理结构（谨慎使用在高频路径）。

> 不改变逻辑，只是减少内存分配、提高缓存友好度。

### 6.2 Timer：从遍历轮询到事件驱动（保持顺序不变）

- 对象：Buff 过期、技能 CD、怪物 AI 间隔、技能 DOT Tick 等。
- 原实现大多是“在 Tick 中全表轮询 + 判断是否到期”。
- 新实现：
  - 使用时间轮（wheel timer）或带时间戳的优先队列统一管理事件。
  - 对同一 Tick 内到期的事件，按**原实现顺序**（例如插入序）进行处理，以保证可预期。

### 6.3 AOI 内部实现优化但逻辑不变

- 仍使用原来的**九宫格 + 全扫描** AOI 算法：
  - 谁能看到谁、广播对象集合保持不变。

- 内部优化：
  - AOI grid 使用连续内存（例如 `Vec<Vec<Cell>>`）。
  - 单格子中的实体列表使用 `SmallVec` 等减少分配。
  - 减少 `clone` 与字符串分配，优先使用 ID / intern 字符串。

### 6.4 阶段 2 验收

- Record/Replay 结果与阶段 1 相比，误差不显著增加。
- 在线压测下 CPU 与内存占用明显下降（预期 30%~50% 优化空间）。


---

## 七、阶段 3：中型优化（仍不改变行为）

这阶段主要整理时间驱动、日志与网络缓冲，仍以行为不变为前提。

### 7.1 统一逻辑帧（Frame）与 Tick Loop

- 从粗糙的 `while (true) { Run(); sleep(10ms) }` 升级为：
  - 维护 `FrameState { dt: Duration, frame_no: u64 }`。
  - 所有系统基于统一 `dt` 驱动，Tick 顺序保持与原服一致。

- 收益：
  - Tick 更稳定，方便监控与调试。
  - 为后续多线程调度与快照保存提供基础。

### 7.2 日志系统异步化

- 替换为 `tracing` + `tracing-subscriber` 异步日志：
  - 通过有界队列 + 后台写盘线程，减少主线程 IO 阻塞。

- 行为约束：
  - 不改变日志内容、级别与关键字段，只改变“写盘方式”。

### 7.3 Packet 缓冲池化

- 把频繁分配释放的 Packet / Buffer 换成可复用的缓冲池：
  - 使用 `Bytes`/`BytesMut` 或自实现对象池。
  - 协议格式与包内容保持完全不变，优化仅限内存布局与分配次数。

### 7.4 阶段 3 验收

- 日志与网络稳定运行，无丢包或日志缺失现象。
- Record/Replay 仍大致符合阶段 1 结果；监控下卡顿尖刺明显减少。


---

## 八、阶段 4：大中型优化（行为需严格对齐）

此阶段引入分片调度、多线程执行等，风险高，但目标仍是“对玩家观感几乎不变”。建议先在**单地图测试服**上试点，验证稳定后再逐步推广到全区。

### 8.1 AI 执行逻辑分片（Scheduling）

**目标**

- 将怪物 AI 计算负载平均摊到多个帧，避免“大波怪物同帧 `Run()` 导致尖刺”。
- 保持怪物对玩家的反应时间、攻击频率、位移轨迹在可接受误差范围内与阶段 1 结果一致。

**数据结构建议**

- 每个地图维护一个稳定排序的怪物列表和调度游标：

```rust
struct MapRuntime {
    monsters: Vec<MonsterId>,      // 按 spawn 顺序或 id 排序
    ai_cursor: usize,              // 本帧从哪个下标开始
}
```

- 怪物运行时可附带上次 AI 执行帧号，用于防止极端饿死：

```rust
struct MonsterRuntime {
    last_ai_tick: u64,             // 上次执行 AI 的逻辑帧号
}
```

**调度算法示意**

- 设目标为“平均每 N 帧执行一次怪物 AI”，则每帧处理 `monsters.len() / N` 左右的怪物：

```rust
fn run_monster_ai(map: &mut MapRuntime, frame_no: u64) {
    let total = map.monsters.len();
    if total == 0 { return; }

    let batch = (total + N - 1) / N;    // 向上取整
    for _ in 0..batch {
        let idx = map.ai_cursor % total;
        let mid = map.monsters[idx];
        map.ai_cursor = (map.ai_cursor + 1) % total;

        // 实际的 AI 逻辑（与阶段 1 中一致）
        run_ai_for_monster(mid, frame_no);
    }
}
```

- 通过 `ai_cursor` + 稳定排序保证：
  - 同一只怪物在多个 Tick 中执行顺序可预测。
  - 怪物之间的决策顺序与原实现尽可能保持一致（例如按 ID 排序）。

**风险与监控**

- 防止个别怪物长时间未执行 AI：
  - 记录 `last_ai_tick`，设置最大间隔阈值，超过则强制执行一次。
- 监控指标：
  - 每帧 AI 执行数量分布（直方图）。
  - 单帧 AI 总耗时与 P95/P99。
  - 怪物攻击间隔、追击延迟与阶段 1 Replay 的偏差。

### 8.2 多线程调度器（Sharded World / Workers）

**目标**

- 在保证单帧逻辑一致性的前提下，将可并行的子系统拆分到多个 Worker，提高 CPU 利用率。
- 避免写冲突和“有人看到新状态，有人还看到旧状态”的竞态。

**分片策略示例**

- 以“地图”为粒度：
  - 每个 Worker 负责若干个 Map 的全部逻辑（AOI / Buff / AI / 环境）。
  - 适用于地图之间交互较少的场景。
- 以“实体 ID 范围”为粒度：
  - 按 `EntityId` 区间分片，保持分片内数据尽量独立。

**单帧调度流程（示意）**

1. 主线程：计算本帧 `FrameState { dt, frame_no }`。
2. 主线程：将各分片本帧要执行的任务（Map/Entity 集合）分发给 Worker。
3. 各 Worker 并行执行本帧逻辑：
   - AOI 更新（只修改本分片内的可见关系）。
   - Buff 更新与到期处理。
   - 怪物/玩家 AI、移动、战斗。
   - Map 环境更新（掉落衰减、环境伤害等）。
4. Worker 将“跨分片影响”的结果写入事件队列（例如：跨图传送、跨分片攻击）。
5. 主线程在帧尾统一处理事件队列，完成全局状态的最终合并（commit）。

**写入规则**

- 普通状态更新：
  - 只能写入本分片“拥有”的实体与地图局部数据。
- 跨分片影响：
  - 不直接修改对方分片的数据，而是写入全局事件队列，由主线程或目标分片在下一帧处理。
- 所有写操作在逻辑上视为发生于**同一帧结束时刻**，保证对所有玩家可见的一致性。

**监控与调试**

- 增加“单线程模拟模式”：
  - 使用与多线程相同的分片与队列逻辑，但在单线程顺序执行，方便对比结果。
- 在 Replay/回放环境中，比较多线程执行与单线程执行的关键事件序列与最终快照差异。

### 8.3 NPC/WASM 脚本引擎替换（可选）

**迁移目标**

- 将 NPC 对话、任务逻辑等脚本迁移到更现代的运行时（WASM/Lua 等），提升安全性与扩展性，同时保持行为一致。

**设计要点**

- 抽象统一的脚本接口，例如：

```rust
trait NpcScript {
    fn on_talk(&mut self, ctx: &mut NpcContext, player_id: PlayerId);
    fn on_select(&mut self, ctx: &mut NpcContext, player_id: PlayerId, option: i32);
}
```

- 旧脚本解释器与新引擎（WASM/Lua）都实现这套接口，支持一段时间内 A/B 共存。
- 为脚本执行增加：
  - 超时限制（防止单个脚本卡死主线程）。
  - 内存上限（防止异常分配）。
  - 日志与 tracing span，方便线上排查。

**迁移步骤示例**

1. 封装一层 `ScriptHost`，屏蔽底层脚本引擎差异。
2. 先将部分“只涉及对话、不改变数值”的 NPC 改为 WASM/Lua，实现 A/B 双跑：
   - 同样输入下比对输出文本、任务/奖励结果。
3. 扩大脚本集覆盖面，逐步迁移任务/奖励/分支逻辑。
4. 最终在验证通过后，停用旧脚本解释器。

**行为一致性约束**

- 对给定 NPC、给定输入（玩家状态、选择项等），旧引擎与新引擎的：
  - 文本内容。
  - 分支走向。
  - 任务状态变更。
  - 奖励结果。
- 必须在行为测试环境中逐一比对通过后才能灰度到线上。

### 8.4 阶段 4 验收

- 高并发压测下，与阶段 3 相比：
  - 单服可支撑在线数明显提升，或相同在线下 CPU 利用率显著下降。
  - 帧耗时分布更平滑（尖刺减少）。
- 在真实玩家体验服上长时间运行（例如 ≥ 7 天）：
  - 未出现大规模“怪物行为诡异”“AI 失控”“战斗节奏被打乱”的反馈。
  - 崩溃率、严重错误告警不高于阶段 3。
- 在 Replay/回归环境下，多线程实现与单线程实现的关键事件序列基本一致。

## 九、阶段 5：高级优化（可能影响行为，需要公告级控制）

此阶段不再承诺 100% 行为不变，而是以“改善体验与长期扩展”为主。需要通过版本公告或灰度方式逐步上线。

### 9.1 AOI 彻底重做

- 从简单九宫格升级为：
  - 更智能的区域分割 / 分层 AOI。
  - 不同实体类型的不同可见半径与更新频率。

- 可能带来的变化：
  - 广播顺序、仇恨构建方式变化。
  - 远处怪物/玩家是否可见的规则改变。

### 9.2 寻路系统重构（风险最大）

- 由原本脆弱的寻路实现升级到更稳定、可配置的算法：
  - 分级寻路、导航网格、带权栅格等。

- 风险：
  - Boss 走位与卡位策略变化，某些“利用旧寻路 bug 的打法”失效。
- 建议：
  - 为每张关键地图提供灰度开关与兼容模式寻路，保留回滚空间。

### 9.3 战斗/数值体系重塑（可选）

- 在 ECS/现代结构稳定后，可考虑：
  - 更精细的命中/暴击/抗性系统。
  - 更丰富的伤害来源与减伤结构。

- 这部分属于“版本更新级别”的内容，不再归类为“透明优化”，需要专门策划与测试。

## 十、与客户端 / ECS / 地图 / 画质演进的衔接

> 本文聚焦服务端，但服务端架构会直接影响未来客户端与工具链的演进。

### 10.1 与客户端 ECS 改造的关系

#### 10.1.1 目标与原则

- 长期目标：
  - **服务端与未来客户端共享一套 ECS 数据模型与核心规则**（组件结构、Buff/技能公式等）。
  - 协议层逐步从“对象快照”演进到“组件 diff / 事件流”，提高带宽利用率与可扩展性。

- 近期原则：
  - 在阶段 0–3 期间，**只做“ECS 友好”的数据和系统设计，不大规模切换到真正的 ECS 框架**，优先保证重写稳定性。
  - 将容易组件化的部分（位置、属性、Buff 列表等）先抽成共享数据结构，为未来客户端改造打基础。

#### 10.1.2 服务端 ECS 分阶段演进

- **Server-ECS-Prep（对应本文阶段 0–2）**
  - 做法：
    - 在 `crystal-server-core` 内部，将玩家/怪物/投射物等实体的数据拆分为若干小 struct：
      - `Position { x, y }`
      - `Direction { dir }`
      - `Attributes { hp, max_hp, mp, attack, defense, ... }`
      - `BuffList { buffs: Vec<BuffInstance> }`
      - `MovementState { speed, move_cooldown, ... }`
    - 逻辑以“函数/系统”形式运作，例如：
      - `movement_system(&mut positions, &movement_states, dt)`
      - `combat_system(&mut attributes, &mut buff_lists, events)`
    - 保持对外接口仍然是当前的 `World/Player/Monster` 结构，不引入真正的 ECS 框架依赖。
  - 产出：
    - 一套相对稳定的“准组件”定义，后续可以直接迁入 ECS。

- **Server-ECS-1（可选，对应阶段 3–4）**
  - 做法：
    - 在内部引入轻量 ECS（如 `hecs` / `bevy_ecs`），先只接管一小部分系统，例如：
      - 投射物（子弹、飞行技能）。
      - 临时召唤物、陷阱类实体。
    - 保留原有 World/Map 接口，对上层逻辑透明。
  - 目的：
    - 试点验证 ECS 在服务端的可行性与收益（并行度、简化逻辑）。

- **Server-ECS-2（长期，对应阶段 4 以后）**
  - 做法：
    - 将怪物/玩家/环境实体逐步迁入 ECS world：
      - World 内部以 Entity + Component 形式存储数据。
      - 现有 `World`/`Map` 结构更多变成 ECS 的“门面 / Facade”。
    - Tick 调度由 “系统调度器 + FrameState” 统一驱动。
  - 要求：
    - 保持与阶段 1 Record/Replay 的行为基本一致。
    - 所有 ECS 改造都需通过回放与压力测试验证。

#### 10.1.3 客户端 ECS 分阶段演进

> 客户端目前仍为 C# + SlimDX 结构，ECS 改造属于中长期目标。

- **Client-ECS-Prep**
  - 做法：
    - 将客户端中的玩家/怪物/特效等渲染对象的数据结构向服务端的“准组件”靠拢：
      - 同名字段、相同含义的枚举与常量。
    - 在协议解析层尽量直接填充这些数据结构，而不是临时字段。
  - 目的：
    - 降低未来迁移到 ECS 渲染/预测时的阻力。

- **Client-ECS-1（新客户端或大改时）**
  - 做法：
    - 新客户端采用 Rust + ECS（如 Bevy/wgpu+ECS）或 C# + ECS 框架：
      - 直接使用共享 crate 中的组件定义（通过 FFI 或代码生成）。
      - 渲染层读取 ECS world 中的 `Position/AnimationState/Sprite` 等组件进行绘制。
    - 网络层从“对象快照”逐步演进到“组件增量更新 + 事件流”。

- **Client-ECS-2（高级阶段）**
  - 把客户端预测、插值、回滚全部建立在 ECS 模型上：
    - 预测移动与动画。
    - 根据服务端快照/事件对 ECS world 做校正。

#### 10.1.4 共享 crate / 目录结构建议

- 建议新增或强化一个共享 crate，例如：`game-model` 或 `crystal-game-model`：
  - **组件定义**：`Position`、`Attributes`、`BuffData`、`SkillId`、`MapId` 等。
  - **枚举与常量**：职业、怪物类型、装备槽位、Buff 标志位等。
  - **基础规则函数**：
    - 伤害/治疗公式。
    - Buff 叠加 / 驱散规则。
    - 通用 CD / GCD 计算逻辑。

- 服务端：
  - 在 `crystal-server-core` 中直接使用这些组件与规则。

- 未来客户端：
  - 通过 FFI / 代码生成 / 共享 Rust crate 等方式，尽可能直接复用相同定义，减少“双写”与逻辑偏差。

### 10.2 地图与格子的现代化

- **现状**：
  - Tile（贴图）与 Cell（格子逻辑层）分离，资源多、维护复杂。

- 服务端方向：
  - 只关心 nav_grid / collision mask 等逻辑数据，不依赖具体贴图。
  - 在配置工具链中，将地图高清贴图与逻辑网格一并生成，服务端仅消费精简后的二进制 nav 数据。

### 10.3 客户端画质与资源演进（简要）

- 在“不重写客户端，但可以修改”的前提下，可以通过：
  - 资源超分（ESRGAN/Waifu2x 等离线处理）。
  - NIS/FSR 等 GPU 超分与锐化 Shader。
  - 渲染分辨率提升 + 后处理（Sharpen/Gamma/对比度）。

- 服务端与这些改动无强耦合，但：
  - 更清晰的地图/角色需要更精确的碰撞与逻辑数据支持（nav_grid 精度更高）。
  - 后续若客户端转向 ECS/骨骼动画，服务端已有的组件化结构可复用。
